### D0. Trước khi deploy — biết cái gì nặng
`docker-compose.prod.yml` service `web` chạy `python manage.py migrate --noinput` lúc khởi động,
tức **mọi migration dưới đây tự chạy khi `docker compose up -d web`**. Vì có 3 migration lấy khoá
dài trên bảng nóng, deploy nhánh này vào **giờ thấp điểm (sau 22:00 hoặc trước 07:00)**, hoặc chạy
migrate tay trước rồi mới up web:
```bash
cd /home/desi/desi-order
docker compose -f docker-compose.prod.yml run --rm -e DB_PGBOUNCER=0 -e POSTGRES_HOST=postgres -e POSTGRES_PORT=5432 web \
  python manage.py migrate --noinput
```
(`migrate` tự **không** áp `statement_timeout`/`lock_timeout` — `config/settings_parts/base.py`
loại lệnh migration khỏi `options`; không cần đặt `DB_LOCK_TIMEOUT_MS=0` bằng tay, nhưng đặt cũng
vô hại.)

### D1. Recreate Postgres với 6 tham số mới (downtime ~30s)
Compose đã thêm `max_wal_size=4GB random_page_cost=1.1 effective_io_concurrency=200
track_io_timing=on log_min_duration_statement=2000 log_lock_waits=on` vào `command:` của service
postgres. `-c` ở command chỉ ăn khi **recreate** container:
```bash
cd /home/desi/desi-order
docker compose -f docker-compose.prod.yml up -d postgres      # recreate, web/worker tự reconnect
docker exec desi-postgres psql -U desi -d desi -c "SELECT name, setting FROM pg_settings WHERE name IN ('max_wal_size','random_page_cost','effective_io_concurrency','track_io_timing','log_min_duration_statement','log_lock_waits')"
```
Đĩa: `pg_wal` có thể phình tới ~4GB (trước 1GB) — kiểm `df -h` còn > 10GB trống trước khi làm.
Kết hợp cùng cửa sổ này với 2.3-A (`pg_checksums --enable`) và 2.1 (role) của
`2026-09-22-postgres-rebuild.md` để chỉ một lần downtime. Quyết định image debian/alpine: ghi ở
runbook đó mục 2.5 — **chưa chốt, chưa đổi**.

### D2. lock_timeout cho web/worker
- Không PgBouncer (hiện tại `DB_PGBOUNCER=0`): settings đã gửi `-c lock_timeout=5000` qua startup
  `options` cho mọi tiến trình trừ `migrate/makemigrations/squashmigrations/sqlmigrate`. Đổi bằng env
  `DB_LOCK_TIMEOUT_MS` (0 = tắt). Restart web/worker/beat để ăn.
- Khi bật PgBouncer (`DB_PGBOUNCER=1`): startup options **không** được gửi (bẫy #2 trong
  `base.py`) → đặt ở tầng role, đúng như statement_timeout trong `2026-07-24-pgbouncer-cutover.md`:
  ```sql
  ALTER ROLE desi SET lock_timeout = '5s';
  ALTER ROLE desi_migrate SET lock_timeout = 0;   -- role migrate nối thẳng Postgres
  ```
- Khi thấy log web `canceling statement due to lock timeout` dồn dập → có DDL/VACUUM FULL/transaction
  treo đang giữ khoá: `SELECT pid, state, wait_event_type, query FROM pg_stat_activity WHERE wait_event_type='Lock'`.

## Cổng chất lượng & security

### 1. JWT: rút vòng đời token (N2/H1) — làm NGAY, 5 phút

Prod đang đặt `JWT_ACCESS_MINUTES=525600` / `JWT_REFRESH_DAYS=365`. Từ MR này code
production **tự kẹp** access > 1440' về 60' và refresh > 30d về 14d (log ERROR
`JWT_ACCESS_MINUTES=… vượt trần …`), nhưng vẫn phải sửa env cho đúng:

```bash
cd /home/desi/desi-order
cp .env .env.bak-$(date +%Y%m%d-%H%M%S)
sed -i 's/^JWT_ACCESS_MINUTES=.*/JWT_ACCESS_MINUTES=60/; s/^JWT_REFRESH_DAYS=.*/JWT_REFRESH_DAYS=14/' .env
grep -n '^JWT_ACCESS_MINUTES=\|^JWT_REFRESH_DAYS=' .env      # phải ra 60 / 14
docker compose -f docker-compose.prod.yml restart web
docker logs desi-web --since 2m 2>&1 | grep -i "JWT_" || echo "OK: không còn cảnh báo kẹp trần"
```

Hệ quả cho người dùng: access token cũ (1 năm) vẫn hợp lệ tới khi hết hạn hoặc
đổi mật khẩu (`token_version`). FE refresh im lặng (`services/http.ts`) nên
không ai bị văng ngay; phiên mới sống 14 ngày nếu có hoạt động.

### 2. Xoay mật khẩu admin từng xuất hiện trong log (N2/H2)

Token WS của mọi user (kể cả admin) nằm trong log 14 ngày qua (`docker logs desi-web`
→ Loki). Đổi mật khẩu = bump `token_version` = vô hiệu mọi token đã phát hành.

```bash
# Liệt kê user_id xuất hiện trong dòng "WebSocket /ws/crm/?token=" 14 ngày qua
docker logs desi-web --since 336h 2>&1 | grep -o 'token=[^ "]*' | sort -u | wc -l
# Decode payload JWT (phần giữa) để lấy user_id — KHÔNG in token ra ticket:
docker logs desi-web --since 336h 2>&1 | grep -o 'token=[^ "]*' | cut -d. -f2 | sort -u \
  | while read p; do echo "$p==" | tr '_-' '/+' | base64 -d 2>/dev/null | grep -o '"user_id":[0-9]*'; done | sort -u
# Với từng user là superuser / role quản trị: đặt lại mật khẩu (ép đổi lần đăng nhập sau)
docker compose -f docker-compose.prod.yml exec web python manage.py changepassword <username>
```

Tối thiểu: mọi tài khoản `is_superuser` + role "Administrator". Mật khẩu mới ≥ 12 ký
tự (validator mới, xem §5).

### 3. Scrub token khỏi log (N2/H2)

- Backend: filter `apps/common/log_scrub.py` tự kích hoạt sau deploy (console Django +
  `uvicorn.access`/`uvicorn.error`), không cần cấu hình.
- Alloy: `monitoring/alloy-config.alloy` có `loki.process "scrub_secrets"` — **restart
  Alloy** sau khi kéo code:

```bash
docker compose -f docker-compose.prod.yml restart alloy
docker logs desi-alloy --since 1m 2>&1 | grep -i "error" || echo "OK"
# Kiểm: 5 phút sau, trong Grafana Explore: {container="desi-web"} |= "token=" → chỉ còn token=***
```

- Log đã vào Loki trước đó (retention 14 ngày, `monitoring/loki-config.yml`) sẽ tự
  hết hạn; không xoá tay (Loki không có API xoá theo dòng ở bản đang chạy). Tới
  ngày +14 kể từ khi Alloy restart thì §2 là đủ.
- Nginx host: `/var/log/nginx/access.log` format mặc định ghi `$request` → có
  `?token=`. Thêm vào `/etc/nginx/nginx.conf` (http context) một `log_format` che
  query cho `/ws/` rồi dùng ở vhost, hoặc tối thiểu:

```bash
sudo sed -i 's/token=[^ &"]*/token=***/g' /var/log/nginx/access.log*   # dọn file hiện có
sudo logrotate -f /etc/logrotate.d/nginx
```

- FE: sau khi frontend deploy bản gửi token qua subprotocol `desi.jwt.v1`, theo dõi
  `docker logs desi-web | grep -c "token đi qua query string"` → về 0 thì release
  sau gỡ fallback `?token=` trong `apps/channels_core/jwt_middleware.py`.

### 4. Security header cho vhost host (C6/M4)

Repo đã cập nhật `nginx/customer.delax.vn.host.conf.example` (server_tokens off,
HSTS/XCTO/XFO/Referrer-Policy/Permissions-Policy, CSP **Report-Only**) và
`frontend/nginx.conf` (image frontend — tự áp khi deploy). Áp lên vhost host thật:

```bash
cd /home/desi/desi-order
sudo cp /etc/nginx/sites-available/customer.delax.vn /etc/nginx/sites-available/customer.delax.vn.bak-$(date +%Y%m%d)
diff -u /etc/nginx/sites-available/customer.delax.vn nginx/customer.delax.vn.host.conf.example | less
# Chép khối "Security header" (server_tokens off + proxy_hide_header + add_header)
# vào NGAY SAU `client_max_body_size 50m;` của CẢ HAI server block (customer + erp).
# KHÔNG thêm add_header vào location nào khác (mất kế thừa).
sudo nginx -t && sudo systemctl reload nginx
curl -sI https://erp.desiglobal.vn/ | grep -i "strict-transport\|x-frame\|x-content-type\|referrer-policy\|content-security-policy-report-only\|^server:"
curl -sI https://customer.delax.vn/api/healthz | grep -ic "strict-transport"   # phải = 1 (không trùng 2 dòng)
```

CSP: giữ Report-Only ≥ 2 tuần, theo dõi console trình duyệt (webphone iframe nạp
`ajax.googleapis.com` + `cdn.zenify.biz`), rồi đổi tên header thành
`Content-Security-Policy` trong cả `frontend/nginx.conf` lẫn vhost.

### 5. Chống brute-force đăng nhập (C6/M5)

Tự bật sau deploy, không cần env:
- Throttle `login_user` 5/phút theo (username, IP) — chỉnh `LOGIN_USER_THROTTLE_RATE`.
- Khoá 15' sau 10 lần sai liên tiếp/username — `LOGIN_LOCKOUT_THRESHOLD`,
  `LOGIN_LOCKOUT_SECONDS`. Mở khoá sớm cho một người: 
  `docker compose -f docker-compose.prod.yml exec web python manage.py shell -c "from apps.users import login_lockout as l; from django.core.cache import cache; k=l.normalize_username('<username>'); cache.delete(f'login_lock:{k}'); cache.delete(f'login_fail:{k}')"`
- Metric: `desi_throttled_requests_total{scope="login_user"|"login_lockout"}` — thêm
  panel/alert nếu tăng bất thường.
- Mật khẩu mới tối thiểu 12 ký tự (`PASSWORD_MIN_LENGTH`), **chỉ áp khi đổi/đặt

### 8. Rule `DOCKER-USER` (N4) — Docker bỏ qua ufw

Chặn mọi kết nối inbound từ ngoài tới port do docker publish, trừ 80/443 (nginx host
không qua docker nên không ảnh hưởng):

```bash
sudo iptables -I DOCKER-USER -i eth0 -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -I DOCKER-USER 2 -i eth0 -p tcp -m multiport --dports 80,443 -j ACCEPT
sudo iptables -A DOCKER-USER -i eth0 -m conntrack --ctstate NEW -j DROP
sudo iptables -L DOCKER-USER -n --line-numbers
# Bền qua reboot:
sudo apt-get install -y iptables-persistent && sudo netfilter-persistent save
```

Thay `eth0` bằng interface public thật (`ip route get 1.1.1.1`). Kiểm từ máy ngoài:
`nc -zv 103.190.36.153 55432` phải timeout.

### P1. `WS_CHANNEL_FANOUT_PHASE=2` (C4) — bật kèm deploy

`docker-compose.prod.yml` đã đổi mặc định `WS_CHANNEL_FANOUT_PHASE` từ 1 → 2. Nếu
`.env` prod đang ghi đè `=1` thì phải sửa/xoá dòng đó, nếu không compose vẫn lấy 1.

Điều kiện: mọi container `web` đang chạy consumer join `CRM_BROAD_GROUP`
(`apps/channels_core/consumers.py`, có từ MR C5 08-19 — bản prod hiện tại đã đủ).
Publisher ở phase 2 chỉ đổi đích bản sao diện rộng từ `crm_updates` sang
`crm_updates.broad`; event không kênh, `restore.completed`, pubsub bridge (Go) vẫn
đi `crm_updates` nên không client nào mất event. Thứ tự:

```bash
grep -n WS_CHANNEL_FANOUT_PHASE .env                     # xoá/sửa nếu đang =1
docker compose -f docker-compose.prod.yml up -d web       # web trước (consumer)
docker compose -f docker-compose.prod.yml up -d worker worker-kiotviet worker-slow worker-export worker-foxia beat
docker compose -f docker-compose.prod.yml exec web env | grep WS_CHANNEL_FANOUT_PHASE   # =2
```

Kiểm:

```bash
# 1) Cấu hình đã vào process (web lẫn worker):
docker compose -f docker-compose.prod.yml exec worker python manage.py shell -c \
  "from apps.orders.application.services.order_event_publisher import _broad_copy_group; print(_broad_copy_group())"
# → crm_updates.broad
# 2) Đếm group_send thật trên channel layer trong 60s (Redis channel layer, DB theo CHANNEL_LAYERS):
docker exec desi-redis-managed redis-cli MONITOR 2>/dev/null | timeout 60 grep -c 'asgi:group:crm_updates.broad'   # >0 khi có đơn mới
docker exec desi-redis-managed redis-cli MONITOR 2>/dev/null | timeout 60 grep -c 'asgi:group:crm_updates"'        # chỉ còn event không kênh (restore, bridge)
```

Vẫn 2 `group_send`/event (group kênh + bản diện rộng) nhưng bản diện rộng chỉ
fan-out tới client scope all/own thay vì MỌI client; sale scope "channels" chỉ nhận
group kênh của mình → số message tới consumer và số bản trùng phải khử (dedup_id)
giảm theo số sale. Rollback: `WS_CHANNEL_FANOUT_PHASE=1` + restart web/worker.

### B1. BẮT BUỘC TRƯỚC DEPLOY: khai 3 biến env nghiệp vụ trong `.env` prod

`config/settings_parts/base.py` không còn default id kênh/kho prod trong code và
**fail-fast (`ImproperlyConfigured`) khi `APP_ENV=production` thiếu** một trong ba biến
dưới đây (trước chỉ WARNING). Container web/worker/beat sẽ **không lên** nếu thiếu.
Giá trị hiện hành lấy từ default cũ trong code (đã chạy prod tới 23/09):

```dotenv
# .env (prod) — thêm 3 dòng này TRƯỚC khi deploy nhánh audit/arch
KIOTVIET_STATUS_SYNC_TARGETS=[{"channel_id": 4, "branch_ids": ["231174", "241190"]}, {"channel_id": 5, "branch_ids": ["30965"]}, {"channel_id": 6, "branch_ids": ["89084"]}]
KOC_CHANNEL_ID=15
SALE_FB_CHANNEL_IDS=24
```

`docker-compose.prod.yml` ĐÃ sửa trong cùng nhánh (commit sau merge audit/arch): cả 3 biến
dùng cú pháp `${VAR:?...}` — thiếu trong `.env` thì `docker compose up` báo lỗi ngay ở
bước render, không để container crash-loop. `KOC_CHANNEL_ID` đã được passthrough vào
`x-backend-env`. Kiểm trước deploy: `docker compose -f docker-compose.prod.yml config >/dev/null`.

Kiểm sau deploy: `docker compose exec web python -c "from django.conf import settings as s;
print(s.KOC_CHANNEL_ID, s.SALE_FB_CHANNEL_IDS, s.KIOTVIET_STATUS_SYNC_TARGETS)"` →
`15 (24,) [...3 target...]`. Ngoài production: thiếu biến → `None` / `()` / `[]` (KOC nhận
diện chỉ theo mã kênh `koc`; cron status không quét gì; báo cáo ads không loại kênh nào).
